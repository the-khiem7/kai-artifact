Terraform thực chiến: cấu trúc repo, quy trình phát triển và pipeline

Tài liệu đào tạo nội bộ, rút ra từ việc vận hành hai repo Terraform thật trên AWS. Chỉ giữ phần kiến thức lõi: tổ chức repo, state, bootstrap, viết code, testing, apply và pipeline GitLab CI. Mọi tên dự án, account, bucket, tên miền và người đã được thay bằng ký hiệu chung.

Cách đọc

Mỗi phần có thể đọc riêng. Khung màu tím là quy tắc nên theo, khung vàng là điểm dễ sai, khung đỏ là điều không được làm. Phần cuối có checklist và bài tập để tự kiểm tra.

1Mô hình tư duy: bốn nơi và một vòng lặp

Mọi lỗi Terraform khó hiểu đều quy về việc nhầm lẫn giữa bốn nơi dưới đây.

  • Code là trạng thái mong muốn, nằm trong Git, ai cũng đọc được.
  • State là sổ ghi mỗi địa chỉ resource (ví dụ module.edge.aws_lb.alb) tương ứng với ID thật nào. Mất state thì Terraform "quên" resource và sẽ tạo trùng.
  • Plan là phép so sánh. Một plan xấu (delete nhầm, replace database) phải bị bắt ở bước này, không phải sau apply.
  • Apply chỉ có nghĩa khi áp dụng đúng plan đã duyệt. Nếu state đổi giữa chừng, plan lưu sẽ bị từ chối là "stale", đó là hành vi đúng.
!
Hệ quả thiết kế

Vì state là nguồn sự thật của Terraform, nó phải nằm ở nơi chung, có lock, có version và có kiểm soát access. Toàn bộ phần repo, bootstrap và pipeline phía sau đều xoay quanh việc bảo vệ ba thứ: state, identity chạy Terraform, và bản plan.

2Cấu trúc repo

Hai directory chính: modules/ chứa phần dùng chung, environments/ chứa nơi thật sự có state.

Cây directory tham chiếu

terraform/
├── modules/                    # building block, KHÔNG có state riêng
│   ├── networking/             # mỗi module: main, variables, outputs, locals
│   ├── data/
│   ├── compute/
│   └── edge/
├── environments/                # mỗi root = một state = một đơn vị triển khai
│   ├── poc/                     # environment thử nghiệm, account riêng
│   └── uat/
│       ├── <stack-a>/
│       │   ├── bootstrap/        # tạo bucket state (chạy một lần)
│       │   └── resource/         # infrastructure thật, dùng bucket ở trên
│       └── <stack-b>/
│           ├── bootstrap/
│           └── resource/
└── archive/                     # code cũ, không được CI scan hay chạy

Root (directory trong environments)

Là nơi chạy terraform init/plan/apply. Mỗi root có đúng một backend, một file state, một key. Root chỉ ghép các module và truyền variable, không nên tự định nghĩa hàng chục resource thô.

Module (directory trong modules)

Là hàm có input (variables.tf) và output (outputs.tf). Module không có backend, không tạo provider, không đọc state của module khác. Mọi thứ nó cần phải được truyền vào.

Vì sao tách bootstrap và resource

Bucket chứa state không thể nằm trong state của chính nó khi chưa tồn tại. Tách thành hai root giải được "con gà - quả trứng" và còn cho ba lợi ích: root bootstrap rất nhỏ nên risk thấp, hai root có chu kỳ thay đổi khác nhau, và bucket state có thể được bảo vệ riêng (chặn delete). Chi tiết ở mục 5.

Chuyển resource vào module thì địa chỉ state đổi

Đưa một resource vào module làm đổi địa chỉ, Terraform hiểu là "delete rồi tạo lại". Khi chưa apply lần nào việc tái cấu trúc này miễn phí. Sau apply đầu tiên mỗi địa chỉ cần một moved block (mục 9) và plan phải được đọc từng dòng. Vì vậy hãy quyết định ranh giới module trước khi infrastructure tồn tại.

Không bao giờ commit

State, file plan, tfvars chứa value thật, private key hoặc certificate có private key. State và plan chứa cả value nhạy cảm dạng chữ thường (mật khẩu database, signing key). Scan diff trước mỗi lần git add.

Ví dụ terraform block và backend

terraform {
  required_version = ">= 1.10"

  backend "s3" {}

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

Backend rỗng là kiểu "partial configuration": code không chứa tên bucket nên cùng một root dùng được cho nhiều environment nếu cần.

bucket       = "<org>-<env>-tfstate-<region>"
key          = "<env>/terraform.tfstate"
region       = "<region>"
use_lockfile = true

Không có profile. Máy runner không có file credentials, nên một profile cố định làm init thất bại. Identity lấy từ environment variable của CI.

provider "aws" {
  region = var.aws_region
  default_tags { tags = local.common_tags }
}

provider "aws" {
  alias  = "us_east_1"   # certificate và WAF của CloudFront phải ở us-east-1
  region = "us-east-1"
  default_tags { tags = local.common_tags }
}

4State và backend

State là tài sản quan trọng nhất của repo. Hãy đối xử với nó như database sản xuất.

Backend từ xa trên S3

  • encrypt = true, bucket encryption mặc định
  • Bật versioning để khôi phục bản state cũ
  • Chặn toàn bộ public access
  • Chủ sở hữu object bắt buộc (BucketOwnerEnforced)
  • Lifecycle: expire bản cũ sau một thời gian (ví dụ 90 ngày)

Lockfile

Từ Terraform 1.10, use_lockfile = true tạo một object .tflock cạnh file state ngay trong S3. Không cần bảng DynamoDB riêng. Hai lần chạy cùng root không overwrite nhau.

Những điều cần nhớ về state

  • State chứa secret. Mọi value đưa vào qua secret_string, mật khẩu database, signing key đều nằm dạng chữ thường trong state và trong file plan. Quyền đọc bucket tương đương quyền đọc các secret đó.
  • Bucket riêng cho mỗi environment, nằm trong cùng account với environment đó. Một bucket chung với nhiều key làm mọi người có quyền ở environment thấp đọc và ghi được state environment cao.
  • Mỗi root một key riêng. Hai root ghi cùng một object sẽ overwrite nhau và mỗi bên thấy resource của bên kia là thứ cần delete.
  • Không dùng workspace để thay cho environment trên state cục bộ: chỉ nhân bản file state trên một máy.
  • Không sửa tay state. state mv, state rm, import, taint đều là thao tác ghi, cần phê duyệt riêng và nên làm qua pipeline hoặc moved block/import trong code.
  • Gặp orphan lock sau khi một plan bị hủy giữa chừng: kiểm tra không có lần chạy nào còn sống rồi mới force-unlock. Đó là lý do job plan trong CI để interruptible: false.

5Bootstrap: tạo bucket state

Vấn đề: Terraform cần bucket để lưu state, nhưng bucket đó cũng muốn được Terraform quản lý.

Các phương án đã cân nhắc

Phương ánKết quảLý do
Apply với state cục bộ, rồi init -migrate-state vào bucketBỏGiữa hai lệnh phải sửa code (thêm backend). Một lần chạy pipeline gắn với một commit nên không làm được, và state phải chuyển tay giữa hai lần chạy
Tạo bằng console rồi importBỏPhần config tạo bằng tay trước khi có code mô tả nó, khoảng trống không được quản lý
Một job vừa apply cục bộ vừa migrateBỏMột job làm hai việc không chạy lại được, gián đoạn giữa chừng để state ở nơi không ai gọi tên được
Truyền file state qua artifact giữa hai lần chạyBỏCông bố state cho mọi người có quyền artifact, expire theo giờ, bỏ rơi bucket nếu lần sau không chạy
Nửa CLI tạo bucket, nửa Terraform nhận bucket (import)ChọnNửa CLI không sinh state nên không có gì để chuyển. State sinh ra trực tiếp trong bucket

Các lớp ngăn chạy lặp

  1. Idempotent: job tạo bucket thoát thành công nếu bucket đã có. Đây là lớp duy nhất không dependency người kiểm tra.
  2. Dấu hoàn thành duy nhất: sự tồn tại của object state trong bucket cho biết bootstrap đã xong chưa. Không trả lời bằng trí nhớ.
  3. Điều kiện đầu của từng job: từ chối nếu thứ tự sai (ví dụ nhận bucket khi bucket chưa có, hoặc import khi state đã có).
  4. Bề mặt kích hoạt: job manual, chỉ hiện khi directory bootstrap thay đổi, dùng chung một resource_group, và prevent_destroy trên bucket.

Import block có gate bằng variable

import {
  for_each = var.adopt_existing_bucket ? toset(["this"]) : toset([])
  to       = aws_s3_bucket.terraform_state
  id       = var.state_bucket_name
}

resource "aws_s3_bucket" "terraform_state" {
  bucket = var.state_bucket_name
  lifecycle { prevent_destroy = true }
}

Import block trỏ tới resource đã có trong state sẽ làm plan lỗi. Nếu không có gate, phải delete block sau khi nhận bucket, tức là thêm một lần sửa code, đúng điều bootstrap muốn tránh. Sau khi apply xong hãy tắt variable, vì nếu để mở thì mọi plan sau đó bị chặn.

!
Cách đọc plan nhận bucket

Ba resource "will be imported" nhưng ba resource thêm mới không đồng nghĩa với nhau: config lifecycle là thêm thật, ownership controls thường là no-op, còn encryption có thể đổi config đang chạy (ví dụ từ key mặc định của S3 sang KMS key). Một dòng thay đổi ngoài tags là tín hiệu dừng. Bất kỳ dòng destroy nào cũng là dừng.

!
Root bootstrap riêng cho từng environment

Không dùng lại root bootstrap của environment khác bằng cách đổi tên bucket. Tên bucket là thuộc tính bắt buộc tạo mới, nên plan sẽ delete bucket cũ rồi tạo bucket mới, kéo theo state của cả environment đang chạy. Cũng không để state bootstrap là file cục bộ chỉ có trên một máy.

6Variable, tfvars và secret

Variable là giao diện của root và module. Làm rõ nó thì phần còn lại dễ đọc.

Khai báo tốt

variable "environment" {
  description = "Tên environment, dùng để đặt tên"
  type        = string
  default     = "uat"

  validation {
    condition     = var.environment == "uat"
    error_message = "Root này chỉ dành cho uat."
  }
}

Quy tắc

  • Luôn có description và type.
  • Value an toàn (cỡ máy, số lượng) có default hợp lý và validation bắt value phi lý.
  • Value đặc thù environment nhưng không phải secret (ID account, tên miền) không có default, buộc người gọi truyền vào.
  • Secret đánh sensitive = true và truyền qua environment variable TF_VAR_* hoặc nguồn secret, không qua file commit.

Thứ tự ưu tiên của value

Cao đến thấpNguồn
1-var và -var-file trên dòng lệnh
2*.auto.tfvars (theo thứ tự chữ cái) rồi terraform.tfvars
3Environment variable TF_VAR_name
4default trong khai báo
x
Bẫy: value quan trọng chỉ nằm trong file bị gitignore

Một dự án có hai value chỉ sống trong uat.tfvars nằm ngoài Git: một cờ đổi load balancer thành nội bộ, và một AMI được pin cho NAT instance. Runner CI không có file này nên plan sẽ replace load balancer thành internet-facing và thay NAT instance, cắt đường ra ngoài. Giải pháp: đưa value an toàn thành default trong code. Chỉ giữ ngoài Git những value thật sự là secret.

x
Bẫy: ID account có default

Nếu code mang sẵn ID account "mong đợi" làm default thì kiểm tra account chỉ so code với chính nó. ID phải đến từ một nguồn độc lập (variable của dự án CI) để so với identity thật mà credential trả về.

7Lock file và version

Hai thứ phải pin: version Terraform và version provider.

  • required_version đặt sàn tối thiểu (ví dụ >= 1.10 vì cần use_lockfile). Trong CI, pin version chính xác qua tag image. Version CI không được cũ hơn bản đã ghi state lần cuối, vì Terraform từ chối đọc state do bản mới hơn ghi.
  • .terraform.lock.hcl pin version và checksum của provider. Commit file này. Không có nó, provider trôi trong khoảng ~> 6.0 và một kiểm tra có thể bắt đầu đỏ vào ngày chẳng ai đổi gì.
  • Lock cả hai platform nếu có người dùng khác nhau: terraform providers lock -platform=linux_amd64 -platform=windows_amd64. Runner chạy Linux, dev machine có thể chạy Windows. Thiếu checksum platform nào thì init trên platform đó lỗi.
  • Module chạy test riêng cũng cần lock file riêng, vì job test chạy init ngay trong directory module.
!
Dấu hiệu bộ test không chạy

Delete lock file mà không delete .terraform làm terraform test báo "unknown provider" và in 0 passed, 0 failed. Số không là tín hiệu bộ test chưa hề chạy, khác với một assertion thất bại. Delete cả hai và init lại.

Nâng provider là một thay đổi có chủ đích: terraform init -upgrade, đọc plan, commit lock file trong cùng merge request. Cũng pin AMI của EC2 instance thay vì dùng "latest", nếu không một image mới của nhà cung cấp tạo ra chuỗi replace chưa ai duyệt.

8Module

Module tốt nhỏ, rõ vai trò và nói thật về những gì nó không làm.

Cấu trúc một module

  • main.tf, variables.tf, outputs.tf, locals.tf
  • README.md: giả định và điều module sẽ không phục vụ
  • tests/ và examples/minimal/
  • .terraform.lock.hcl nếu có test

Ranh giới

  • Không tạo provider, nhận từ root qua providers = {}
  • Không đọc state của module khác
  • Mọi thứ cần thiết đi vào qua variable, mọi thứ cho người khác đi ra qua output
  • Dependency đi một chiều: root truyền output của module này làm input module kia

Đặt tên theo vai trò, không theo hình dạng AWS

Module security-group hứa sự tổng quát mà thực tế từ chối. Module broker-security yêu cầu một bộ port cụ thể và không mở dải bất kỳ. Tên là thứ người đọc tin trước khi mở file, nên tên phải đúng với mức tái sử dụng thật. README mỗi module nêu giả định và điều sẽ không phục vụ, vì Terraform không có tham số mô tả cấp module.

Khi nào tách module

TáchGiữ ở root
Nhóm resource có người dùng thứ hai (environment testing phải dựng lại mạng)Resource được nhiều module dùng chung mà không module nào sở hữu (ví dụ KMS key dùng cho log, ổ đĩa và secret)
Nhóm có lifecycle, quyền access hoặc người duyệt riêngMột hay hai resource không có logic riêng. Bọc để đạt "không resource trong root" chỉ thêm một lớp không mang quyết định nào

Truyền provider và gate điều kiện

module "edge" {
  source = "../../../../modules/edge"

  providers = {
    aws           = aws
    aws.us_east_1 = aws.us_east_1   # module cần certificate ở vùng khác
  }

  vpc_id            = module.networking.vpc_id
  public_subnet_ids = values(module.networking.public_subnet_ids)
}

Chuỗi dependency đọc được ngay từ các đối số: networking cho ra vpc_id, edge nhận vào. Không có depends_on khi tham chiếu thuộc tính đã đủ biểu đạt thứ tự.

9Provider, default_tags và account guard

Pipeline lấy identity từ environment variable, nên config phải tự bảo vệ mình khỏi chạy nhầm account.

data "aws_caller_identity" "current" {}

resource "terraform_data" "account_guard" {
  input = data.aws_caller_identity.current.account_id

  lifecycle {
    precondition {
      condition     = data.aws_caller_identity.current.account_id == var.workload_account_id
      error_message = "Đang đăng nhập account ${data.aws_caller_identity.current.account_id}, khác workload_account_id. Dừng."
    }
  }
}
  • Dùng precondition chứ không dùng check block: check chỉ cảnh báo, plan sai account vẫn đi tới nút apply.
  • Test có một run kiểm tra guard: truyền ID sai và dùng expect_failures = [terraform_data.account_guard].
  • default_tags ở provider gắn tag cho mọi resource. Lưu ý quyền IAM: nếu identity CI bị giới hạn bằng permission boundary thiếu TagInstanceProfile, tag mặc định vẫn lan xuống tags_all dù bạn đã bỏ tag trong từng resource, và apply lỗi giữa chừng. Cấp quyền tag cho từng loại resource đang tạo.
  • Tên resource IAM có path (/tf-managed/) giúp boundary giới hạn đúng phần Terraform được phép đụng.

10Import và moved: sửa state bằng code

Mọi thay đổi state nên là thay đổi trong Git, được review và chạy qua pipeline.

import

Đưa resource có sẵn ngoài Terraform vào state. Plan cho thấy "will be imported" trước khi áp dụng.

import {
  to = module.networking.aws_vpc.main
  id = "vpc-xxxxxxxx"
}

moved

Đổi địa chỉ khi đổi tên hay chuyển vào module, tránh delete rồi tạo lại.

moved {
  from = aws_s3_bucket.state
  to   = module.state.aws_s3_bucket.this
}
  • Plan phải ghi rõ "N to import" và 0 delete. Một dòng destroy nghĩa là import khớp sai địa chỉ.
  • Import block chỉ cần một lần. Sau khi áp dụng có thể delete hoặc giữ dormant có gate như ở mục 5. Một block trỏ tới resource đã nằm trong state làm plan lỗi.
  • Import block xung đột với mock_provider (mục 11): test báo "Cannot import resources from mock providers".
  • Dùng terraform plan -generate-config-out để lấy khung code cho resource có sẵn, rồi dọn lại bằng tay.

Cấu trúc file pipeline

Thêm một stack mới là thêm một file stack, một directory policy, một directory fixture và variable có phạm vi riêng. Dùng !reference chứ không dùng YAML anchor để chia sẻ rules, vì anchor không phân giải qua các file được include.

Rules: gate là điều kiện, không phải thứ tự stage

.gate_rules:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH

Ba luật này chạy mỗi job đúng một lần. Nếu chỉ có hai điều kiện "merge request" và "branch", một lần push lên branch có merge request mở sẽ tạo hai pipeline và hai trạng thái có thể mâu thuẫn nhau.

.protected_manual_rules:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: never
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH && $CI_COMMIT_REF_PROTECTED == "true"
      when: manual
      allow_failure: true

Job plan manual, chỉ trên protected ref. CI variables chứa AWS key cũng được bảo vệ nên chỉ job trên protected ref mới nhận được nó.

.tf_apply:
  script:
    - test -s "$PLAN_FILE" || { echo "Refusing apply: missing plan"; exit 1; }
    - terraform show -json "$PLAN_FILE" > /dev/null
    - grep -qx "plan_sha256=$(sha256sum "$PLAN_FILE" | cut -d' ' -f1)" risk-verdict.txt
    - grep -qx "decision=PASS" risk-verdict.txt
    - terraform apply -no-color -lock-timeout=300s "$PLAN_FILE"
  rules:
    - if: $CI_COMMIT_BRANCH && $CI_COMMIT_REF_PROTECTED == "true"
      when: manual
      allow_failure: false

Mọi luật giữ điều kiện $CI_COMMIT_BRANCH: variable này rỗng ở pipeline tag, nên protected tag không bao giờ chạm tới plan hay apply.

!
Không bao giờ dùng $CI_DEFAULT_BRANCH

Nếu quy ước của repo release giữ default branch luôn rỗng và code nằm ở các branch version, một luật gắn vào default branch không khớp ref nào mang code. Kết quả là job plan và apply không bao giờ xuất hiện. Hãy kiểm tra điều này trước khi hứa với ai rằng một job sẽ chạy.

!
needs không phải là gate

needs làm job apply đợi plan và risk, nhưng job risk được phép thất bại (allow_failure) nên nếu chỉ dựa vào needs, apply vẫn chạy. Gate thật là bước kiểm tra nằm trong chính script apply: có file plan, hash plan khớp verdict, verdict là PASS.

Identity và secret trong CI

  • AWS key nằm trong variable CI (masked, protected). Không có file credentials trên runner, không in ra log, không đưa vào tài liệu hay chat. Masking chỉ che đúng chuỗi nguyên văn: value bị encryption base64 hay tách ra vẫn lộ. Masking giảm tai nạn, không phải kiểm soát access.
  • Identity Terraform CI tách khỏi identity chỉ đẩy image. Đừng mở rộng quyền của identity hẹp có sẵn.
  • Có thể dùng OIDC (không có long-lived key) nếu tổ chức chịu lập nhà cung cấp identity. Khi chưa thì static key nằm trong variable protected và có chu kỳ xoay.
  • Variable dài ít ký tự và không secret không được đánh masked: GitLab từ chối, và nếu được thì sẽ che mất chữ đó trong plan.
  • Một variable ID account riêng (không masked) được shell guard và TF_VAR_workload_account_id cùng đọc, để code và identity so với nguồn độc lập.
  • Child pipeline khai inherit: variables: false và tự truyền variable cần thiết. Nếu không, global variable của parent pipeline như TF_ROOT overwrite variable của con và job bootstrap có thể plan nhầm root production. Thêm một câu khẳng định TF_ROOT ở đầu job như lớp thứ hai.
  • Nhóm account hạn chế (Community Edition) không có protected environment hay deployment approval. Khi đó chốt chặn là: when: manual, protected ref, chỉ Maintainer được push. Quy tắc "người duyệt khác người bấm" là thỏa thuận giữa người với người và không có gì ép buộc.

Artifact của job plan

  • tfplan (nhị phân), plan.txt (đọc được), change-report.md, risk-verdict.txt, infracost-report.txt.
  • access: developer và expire_in: 7 days. Value secret xuất hiện trong plan nên artifact là dữ liệu nhạy cảm.
  • Job plan interruptible: false và dùng resource_group chung với apply để hai job không giữ state lock cùng lúc.
  • Job ước tính chi phí lọc bỏ mọi trường secret_string khỏi plan JSON trước khi gửi ra service ngoài, rồi delete file tạm. Việc gửi dữ liệu ra service bên thứ ba cần được phê duyệt riêng.

15Scan chính sách và scoring risk

Ba lớp: scan secret, scan config, và scoring chính plan.

trivy secret

Scan toàn bộ repo tìm key và token, vì secret có thể bị commit ở bất kỳ đâu. Không có danh sách path.

trivy config và checkov

Scan code IaC theo danh sách path viết ra từng dòng. Thêm module hay root mới là một thay đổi được review trên danh sách này.

Rego risk

Conftest scoring bản plan: LOW, MEDIUM, HIGH, CRITICAL. Verdict gắn với hash của chính file plan.

Quản lý exception (suppression)

  • Exception đặt ở lệnh gọi CI (variable CHECKOV_SKIP, file .trivyignore truyền bằng --ignorefile), không đặt chú thích trong code. Cả hai scanner được nối đối xứng để không bên nào giấu thứ bên kia hiển thị.
  • Hệ quả phải chấp nhận: một exception có hiệu lực trên mọi path đang scan, không chỉ một resource. Lý do của từng mục nằm ở sổ quyết định, không nằm trong code.
  • Exception không phải khắc phục. Một exception giống hệt một bản sửa nếu lướt qua, nên mỗi mục ghi lý do và test bù đắp nếu có.
  • Cẩn thận với bất đối xứng công cụ: trivy chạy với --severity HIGH,CRITICAL còn checkov chạy không lọc, nên checkov làm đỏ pipeline vì thứ trivy không hề báo.
  • Scan báo sạch không có nghĩa resource đúng với sản xuất. Ví dụ: một secret tạo với cửa sổ khôi phục bằng 0 ngày delete ngay lập tức, không scanner nào báo.

16Bài học thực chiến

Những lỗi đã xảy ra thật. Mở từng mục để xem vì sao nó trông hợp lý và cách sửa.

Hai pipeline cho một lần push

Trông hợp lý vì: điều kiện "merge request" và "branch" đọc như hai lựa chọn của một sự kiện.

Thực tế: chúng là hai pipeline GitLab tạo từ cùng một lần push. Merge request hiển thị hai trạng thái có thể mâu thuẫn, thời gian chạy nhân đôi.

Sửa: chuỗi ba luật có branch when: never ở giữa, định nghĩa một lần và dùng lại qua !reference.

Protected tag đi thẳng tới apply

Trông hợp lý vì: CI_COMMIT_REF_PROTECTED được đọc là "protected branch".

Thực tế: nó đúng với cả protected tag. Ở pipeline tag, CI_COMMIT_BRANCH rỗng, nên các job scan bị bỏ qua nhưng plan và apply vẫn có mặt: một lối tới apply không có policy nào đứng trước.

Sửa: mọi luật mang điều kiện $CI_COMMIT_BRANCH, và plan khai báo needs vào các job gate.

Luật gắn vào default branch không bao giờ khớp

Thực tế: quy ước release giữ default branch rỗng vĩnh viễn, nên ba job plan, apply và bootstrap không hiện trên bất kỳ ref nào. Pipeline đầu chỉ có năm job scan và nhìn có vẻ xanh.

Sửa: bỏ hẳn $CI_DEFAULT_BRANCH; apply yêu cầu protected ref, plan và bootstrap chạy ở bất kỳ branch nào có điều kiện thay đổi.

Gate trivy đỏ vì cờ bị gỡ, scan thành không scan

Trông hợp lý vì: cờ --no-progress có ở các version trước.

Thực tế: ở version pin, đó là lỗi tham số và job thoát trước khi scan thứ gì. Nó đọc như một lỗi chính sách trong khi tư thế bảo mật chưa hề được đo. Gỡ cờ thì gate bật lên và lập tức báo một phát hiện mức cao ở bucket state.

Bài học: khi một job scan lỗi, hãy kiểm tra nó có thực sự scan không (bảng Report Summary, số lượng file). Nếu tắt cờ phải ghi lý do bên cạnh để không ai thêm lại.

Child pipeline plan nhầm root

Thực tế: child pipeline nhận variable TF_ROOT của cha, vốn ưu tiên cao hơn variable con tự khai. Job plan của bootstrap chạy trên root sản xuất. Khi đó chỉ một việc tình cờ ngăn tai nạn: các variable kích thước chưa có value.

Sửa hai lớp: inherit: variables: false ở trigger, và job khẳng định TF_ROOT ở bước đầu.

Bài học: một cơ chế an toàn hoạt động vì lý do khác là một cơ chế sắp variable mất.

Plan lưu bị "stale"

Thực tế: retry job apply sau khi một lần apply trước đã ghi state làm serial tăng. Terraform từ chối file plan cũ. Chạy lại job plan để có artifact mới. Đây là hành vi đúng: nó chặn bạn áp dụng một kế hoạch tính trên trạng thái không còn tồn tại.

Apply lỗi giữa chừng do permission boundary

Thực tế: identity CI bị boundary chặn iam:CreateRole, rồi iam:TagInstanceProfile. default_tags khiến tag vẫn lan xuống dù đã bỏ tag trong từng resource. Mười tám resource đã tạo trước khi lỗi.

Sửa: mở rộng boundary đúng phạm vi path /tf-managed/, plan lại để có artifact khớp serial mới, rồi apply.

Đọc nhầm lý do "No changes" khi chưa chạy

Thực tế: một tài liệu ghi pipeline "chưa từng chạy" trong khi đã có pipeline thất bại, và ghi code "chưa commit" trong khi đã commit từ hôm trước. Những tuyên bố về trạng thái phải được đo (đọc API, đọc log), không suy ra từ trí nhớ.

Tái cấu trúc module sau khi có state

Thực tế: root có 27 resource thô được chuyển vào bốn module khi chưa apply. Số resource 27 trước và sau, chỉ di chuyển. Cái giá bằng không vì chưa có state. Sau apply, mỗi địa chỉ cần một moved block.

Một apply overwrite secret người khác điền

Thực tế: thêm một key vào secret config làm Terraform ghi version mới từ tfvars, trong đó các value do nhóm khác quản lý đang để trống. Ứng dụng mất kết nối ở lần khởi động sau.

Quy tắc: infrastructure chỉ tạo key rỗng cho value người khác điền. Trước mỗi apply, soát mọi aws_secretsmanager_secret_version được cập nhật hay replace. Gặp thì dừng và hỏi chủ sở hữu.

Một apply làm lùi version image đang chạy

Thực tế: service ECS bỏ qua task_definition vì job triển khai quản lý nó. Một apply đăng ký bản task definition mới mang tag cũ trong config, rồi có người trỏ service vào đó. Environment chạy bản cũ trong khi image registry và pipeline đã giữ bản mới.

Quy tắc: trước khi sửa file ECS, đọc tag thật đang chạy từ API rồi cập nhật variable. Không đọc từ terraform plan vì plan không hiện nó.

Pin AMI: image mới tạo chuỗi replace

Thực tế: tra AMI "mới nhất" qua SSM hay most_recent làm plan tự đề xuất thay máy khi nhà cung cấp release image mới.

Sửa: truyền AMI tường minh, đọc từ máy đang chạy. Nâng AMI là một thay đổi config có plan được duyệt.

Assertion trên value "known after apply"

Thực tế: assertion trên tập route của route table hay subnet_id của instance lỗi "Unknown condition value" ở plan-mode.

Sửa: viết lại trên thuộc tính đã config tương đương, hoặc ghi rõ điều gì chưa được kiểm chứng.

17Checklist và bài tập

Dùng để tự soát trước khi mở merge request và để kiểm tra người mới.

Trước khi mở merge request

  • terraform fmt -recursive sạch
  • validate và test xanh cục bộ
  • Không có state, plan, tfvars thật, key trong diff
  • Lock file được commit nếu nâng provider
  • Variable mới có description, type, validation
  • Value an toàn là default trong code, secret không nằm trong code
  • Resource chuyển module có moved block
  • README module và tài liệu quyết định được cập nhật cùng lượt

Trước khi bấm apply

  • Đã đọc cả plan, không chỉ dòng tổng
  • Không có replace ở resource có dữ liệu
  • Không có secret version bị cập nhật ngoài dự kiến
  • Risk verdict là PASS và khớp hash file plan
  • TF_ROOT và account in ra đúng
  • Không có lần chạy nào khác đang giữ lock
  • Có người thứ hai đã xem plan (thỏa thuận, không có gì ép)

Bài tập

  1. Dựng root nhỏ. Tạo một root có terraform.tf, backend.hcl, một module networking và một test kiểm tra value mặc định cùng expect_failures cho một validation.
  2. Bootstrap. Mô tả bằng lời vì sao không thể tạo bucket state bằng đúng root dùng bucket đó. Vẽ lại ba bước của Hình 3 và nêu điều gì xảy ra nếu bỏ gate variable ở import block.
  3. Đọc plan. Cho một plan có dòng aws_lb.mqtt must be replaced (internal = true to false). Phân loại mức risk, nói vì sao nó cắt mạng và viết một luật Rego bắt nó.
  4. Viết rules. Viết rules cho job apply chỉ chạy trên protected branch, loại pipeline tag và merge request. Giải thích vì sao không dùng $CI_DEFAULT_BRANCH.
  5. Sự cố. Một retry apply báo Saved plan is stale. Liệt kê ba bước xử lý đúng thứ tự và ba việc không được làm.
  6. Thêm stack. Liệt kê các file cần thêm khi thêm một stack thứ hai vào pipeline (file stack, policy, fixture, variable có phạm vi, path scan).
